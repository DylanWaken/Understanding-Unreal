Shade a secondary surface once, then reuse it

Suppose thousands of queries from Sponza's shaded arcade hit the same sunlit wall. Tracing each ray already costs work. Evaluating the wall material and its illumination independently at every hit repeats another large computation. Instead, place a reusable material-and-lighting representation on the wall. A ray hit can then answer “what radiance leaves this part of the wall?” with a lookup.

For a diffuse wall, outgoing radiance is independent of outgoing direction. That is the crucial simplification. We can store one RGB value per surface location rather than a complete function over outgoing directions. A glossy wall does not satisfy this assumption; the cache's effective fully rough response is an approximation whose limitations will matter for reflections.

Choose a surface parameterization

A traditional texture uses authored UVs. Lumen instead builds a set of oriented cards that capture the mesh from useful directions. The offline mesh-card builder samples visible surfaces from axis-oriented views, creates surfels, rejects unsuitable interior samples, clusters coverage into rectangles, and limits the card budget. At runtime, mesh instances transform this representation into the scene. Merged instances and heightfields have additional paths.

Why multiple cards? A single projection of a column cannot represent all of its sides. A projection of the whole atrium hides its arcade interiors behind the outer surfaces. Separate meshes and sufficient card coverage give the cache addressable surfaces where rays actually hit. A magenta region in a coverage visualization is a clue about missing representation, not Monte Carlo variance.

Start a small implementation with one known rectangular wall and one orthographic capture. Store its world-to-card transform, oriented bounds, normal, and texel scale. Once world positions map reliably to capture pixels, add six possible projection directions, coverage selection, and per-mesh card sets. Keep a capture-depth test: the queried point must correspond to the represented surface layer, not another surface that shares the same projected coordinates.

Separate logical surface resolution from physical memory

A distant wall does not need the same cached resolution as a nearby one. Each card therefore needs a logical resolution and page coordinates independent of its current physical atlas placement. A virtual page table maps these coordinates into a finite physical page pool. It also needs enough state to distinguish unmapped, allocated-but-uninitialized, and valid captured data. Sampling stale memory after eviction can look like lighting from an unrelated object.

card_position = world_to_card * hit_position
uv = card_position.xy / card_extent.xy * 0.5 + 0.5
virtual_texel = uv * virtual_resolution
page_xy = floor(virtual_texel / page_payload_size)
within_page = virtual_texel - page_xy * page_payload_size
entry = page_table[card_id, mip, page_xy]
if not entry.resident or not entry.capture_valid: return unsupported
atlas_texel = entry.physical_origin + border + within_page
if not capture_depth_matches_hit(atlas_texel, card_position.z): return unsupported
return sample_final_lighting(atlas_texel, footprint)

This is a minimal address contract, not a byte-for-byte transcription of Unreal's packed helpers. The engine also handles card selection, neighboring contributions, mip/border filtering, virtual-to-physical scale/bias, and depth/normal weighting. The captured texel replay exposes those actual mappings and packed values for one recorded query. Keeping this distinction prevents a teaching pseudocode implementation from being mistaken for the engine's exact binary layout.

Page scheduling needs requests, priority, a work budget, and eviction. A useful priority considers projected importance, distance, lighting changes, and age. Updating everything removes temporal staleness but defeats the budget; updating only what was visible last frame fails on newly revealed surfaces. Dirty material, geometry, and lighting changes have different consequences: a changed material can require recapture, while a moving light may require lighting updates on otherwise valid material pages.

To watch this system over time, track three separate objects. The card bounds describe which part of the mesh can be captured; the page mapping describes where a requested resolution resides; the lighting values describe the most recent estimate stored there. Moving the camera need not move a static wall's card, but it can change its requested resolution and residency. Changing the sun need not move the card or reallocate its page, but it changes the lighting that the page should contain. A static rectangle is therefore compatible with an actively updating cache. Conversely, a rectangle moving across the screen may only reflect camera motion.

Capture material properties before caching illumination

Render the selected card views into depth and material atlases. These are views of the actual material program, not samples copied from the camera GBuffer. Cache capture resolution, normal maps, alpha masks, texture filtering, and view-dependent material logic can therefore produce different results from the primary view. The capture's effective albedo also folds in a fully rough specular approximation in the inspected implementation. It is not always the original material's diffuse base color.

Store the distinction explicitly: effective albedo is dimensionless; emissive radiance has radiance units; direct and indirect irradiance have irradiance units; final lighting represents diffuse outgoing radiance. The audited combine operation is

\[ \widetilde L_{\rm card}(y)=L_{e,\rm card}(y)+\frac{\rho_{\rm eff}(y)}{\pi} \left[\widetilde E_{\rm direct}(y)+\widetilde E_{\rm indirect}(y)\right]. \]

A numerical example makes the contract useful. With effective albedo (0.6,0.3,0.1), zero emission, and total irradiance (10,10,10), the outgoing radiance is approximately (1.910,0.955,0.318). A secondary ray returns that colored radiance. The receiver later applies its own material. Multiplying by the wall's albedo again at lookup would darken it twice.

The atlases store pre-exposed values. If the cache scale is \(e_c\), a stored final-lighting texel is \(L_{\rm card}^{\rm stored}=e_c\widetilde L_{\rm card}\). Convert using the cache's scale when moving into scene-linear or view-pre-exposed space. The current view can have a different scale \(e_v\). A raw numeric comparison across these buffers is invalid until that conversion is explicit.

Illuminate the cards, then let them illuminate each other

Direct card lighting evaluates the lights affecting the represented surface, with its own shadowing path. In this source snapshot, card lighting seeds mask tiles with attenuation, light-function, and cloud-transmittance terms, then resolves required visibility using distance-field or hardware traces; it does not simply sample the primary view's VSM shadow result. It also cannot reuse the camera's final lit pixel: many card texels are off screen, and the receiver normal and material projection may differ. Light lists, shadow masks, card texel positions, and light parameters are therefore part of the cached computation.

For indirect lighting, distribute gather locations over card space, trace their directions, evaluate available scene radiance at hits, integrate irradiance, and reconstruct it across the card texels. These are radiosity probes on cards. They are neither the camera's screen probes nor the separate world-space radiance-cache probes. Their purpose is to update lighting on secondary surfaces.

Place a radiosity probe by choosing a sample in the card's capture domain, decoding its surface depth, and transforming that point back into the scene. This makes the gather follow the represented wall or column rather than a free-standing world grid. Its normal and capture validity determine which surface is being sampled. A card-space grid drawn as a flat rectangle can hide this depth reconstruction; the scene view should place the samples on their reconstructed surfaces. The resulting low-order directional coefficients support a later irradiance reconstruction on that card. They are not the camera pixel's diffuse output, and their four-coefficient, PDF-weighted hemisphere projection has a different normalization from the screen probes' nine-coefficient sphere average.

Project the measured hemisphere without losing its units

A radiosity sample stores four coefficients per color channel: one constant basis function and three first-order directional functions. Let \(Y_j\), \(j=0,\ldots,3\), be that real SH basis, \(e_c\) the cache pre-exposure, and \(p_H\) the hemisphere sampling density. The source's coefficient estimator has the form

\[ c_j^{\rm stored}\approx\frac{1}{N}\sum_{k=1}^{N} Y_j(\omega_k)\frac{e_c\,\widetilde L_i(\omega_k)}{p_H(\omega_k)}, \qquad p_H=\frac{1}{2\pi}\quad\text{for the uniform-hemisphere permutation}. \]

The PDF correction supplies the hemisphere measure. Do not borrow the extra normalization used by the screen probes' sphere-average representation. Irradiance is reconstructed by a dot product with the cosine-transfer coefficients: band zero receives \(\pi\), and band one receives \(2\pi/3\). The resulting stored irradiance is divided by \(e_c\) to recover scene-referred irradiance; a unit-albedo Lambertian outgoing radiance divides once more by \(\pi\). Here \(e_c=0.0625\), captured from the card-lighting parameter block.

Check the convention with a constant unit incident field over the surface hemisphere. Its irradiance should be \(\pi\), and its unit-albedo diffuse outgoing radiance should be 1. The independent 65,536-direction check reconstructs irradiance 3.14159811; the approximately 0.00017% residual against exact \(\pi\) comes from the source's rounded SH basis constants. This validates the normalization convention. It does not prove that low-order SH reproduces every sharp lighting pattern: truncating the directional function remains an approximation.

Share the incoming light field near the visible receiver

The Surface Cache made a secondary hit cheaper. We still cannot afford a large hemisphere of rays at every pixel. Look again at the arcade floor: neighboring pixels on the same smooth patch see similar incident light. Instead of tracing a full directional distribution at each pixel, trace at a sparse set of representative surface positions and reconstruct the answer for nearby pixels.

A screen probe is one such surface sample together with a directional representation of incoming radiance. “Screen” describes how we choose the sample, not a volume floating at a constant camera depth. Its origin comes from a surface position reconstructed using depth. The probe's normal, depth, material-related sampling information, and identity are essential state.

Place probes before tracing rays

A minimal implementation chooses one depth sample per regular screen tile. That works for a flat floor and fails at silhouettes: a column may occupy only a few pixels and receive no representative. Add adaptive probes for uncovered depth/normal configurations. Budget and bound the adaptive count, assign stable indices, and write a map from pixels or tiles to candidate probe identities. The interpolation stage will need that map; allocation order alone is not a spatial relationship.

Invalid depth, sky pixels, backface-supported materials, thin geometry, and normal discontinuities require deliberate rules. A probe origin displaced too far from the surface can cross a wall. Too little offset can self-intersect. Jitter changes the sample pattern over time and must be recorded alongside temporal reprojection. The exact spacing and directional resolution are quality-dependent settings, not universal properties of “a Lumen probe.”

Imagine sliding the camera sideways while keeping one screen tile highlighted. Its depth sample can move along the floor, cross a column silhouette, and then land on the far wall. The tile index has stayed the same while the represented surface has changed. This is why a temporal probe display must show world positions or geometric correspondence as well as atlas indices. Reusing coefficients solely because the integer index matches would carry one surface's illumination onto another. Adaptive probes add a second source of change: their count and compacted order follow current demand, so an adaptive index is not a permanent scene landmark.

Build the first working placement and gather pipeline

Use separate records for the receiver and the traced directions. A minimal receiver record contains world position, geometric/shading normal as required, device or linear depth with a declared convention, screen coordinate, and validity. A ray record contains its owning probe, directional cell, refinement level, direction, trace interval, and result state. An atlas coordinate is not a replacement for the owner identity: compaction changes queue order.

// Teaching implementation: five dispatches with explicit dependencies.
PlaceUniform:
    for each screen tile:
        choose a valid depth sample using the frame's declared jitter
        reconstruct world position with this view's inverse projection
        write UniformProbe[tile] and its geometry

FindUnrepresented:
    for each valid pixel:
        test the uniform probe against this pixel's depth and normal
        if incompatible: mark a demand in an adaptive allocation cell

AllocateAdaptive:
    prefix-sum unique demands; cap at the allocated capacity
    write AdaptiveProbe[base + offset] and pixel/cell-to-probe indirection
    record overflow explicitly; never write beyond the probe array

GenerateDirections:
    for each valid uniform or adaptive probe:
        generate the directional cell/refinement records
        write owner indices before any later queue compaction

TraceAndReconstruct:
    trace the screen route; compact unresolved records
    trace the selected world route; fill each original result slot
    reconstruct directional cells; integrate and interpolate to pixels

A prefix sum is a parallel version of assigning consecutive indices to marked items. If demand flags are [1,0,1,1], an exclusive prefix sum is [0,1,1,2]; the marked items write to indices 0,1,2 and the total count is 3. For several demands in the same allocation cell, deduplicate or use one atomic claim before scanning. Otherwise repeated pixels spend the entire adaptive budget on the same surface.

On the GPU, put the count and capacity in different fields. The count determines active work; capacity determines legal addresses. A subsequent indirect dispatch uses the compacted count, rounded up to the thread-group size, while every shader guards its final partial group. The render graph must order producer writes before consumers and declare the access transition. A CPU readback of the count between every stage would serialize the frame and erase much of the benefit.

The captured Sponza frame gives this distinction a concrete failure case. Its placement allocation has 3,600 uniform slots and capacity for 1,800 adaptive probes. The captured adaptive allocator says 117, supported by 117 nonzero entries in the tile header. Of the uniform slots, 3,569 have finite positive geometry, giving 3,686 active placements with usable geometry. Scanning the entire storage for positive values would instead find 3,809: 123 additional adaptive entries contain old values beyond the active allocation. Drawing those stale entries as current probes would make the visualization wrong even though every plotted coordinate was read from a real buffer. The placement record retains both the active subset and the excluded storage, with the allocator/header evidence and its readback limitations.

The production implementation has additional classification, allocation, and packed representations. The essential invariant survives all of them: every returned direction must remain associated with the receiver and directional measure that generated it. This is why a probe visualization needs the placement map, adaptive count, ray index mapping, and validity data alongside the colorful radiance atlas.

Store directions on a sphere, not just an RGB average

Suppose the courtyard is bright to the right and the covered arcade is dark to the left. Two surfaces at the same position but with different normals receive different irradiance. A single average color cannot capture that. Store radiance as a function of direction, then integrate it against the receiving material.

The inspected implementation uses equal-area spherical mapping for relevant directional probes. Do not substitute the common two-channel octahedral normal mapping and assume equal solid angles. The mapping function, resolution, bin centers, randomized offsets, and Jacobian determine how a texel corresponds to a direction and measure. A visualization should show that mapping beside the radiance, because a bright atlas texel is meaningless without its represented direction.

In the simplest implementation, trace one jittered direction in each equal-area bin. For M bins covering the sphere, each bin has solid angle \(4\pi/M\). Sum radiance times the positive receiver cosine and this measure to estimate irradiance. If directions instead come from a probability distribution, use their inverse-PDF weights. A deterministic quadrature weight and a stochastic PDF are related tools, but not interchangeable labels.

Spend directions where the material and illumination need them

A diffuse receiver prefers directions with large cosine. A glossy receiver prefers directions near its reflection lobe. The last frame's lighting also predicts where bright incoming directions may lie. Lumen's probe tracing can use BRDF and lighting information to guide its directional work. This requires both a distribution and a reproducible mapping from sample indices to generated directions.

To implement a first importance sampler, build nonnegative bin weights \(a_j\), add a small support floor, normalize to \(P_j=a_j/\sum_k a_k\), select a bin through a cumulative distribution or hierarchical reduction, then sample within it. If its solid angle is \(\Delta\sigma_j\) and sampling within the bin is uniform, the directional PDF is \(p_\sigma=P_j/\Delta\sigma_j\). The generated sample must retain enough information to reconstruct that PDF or its encoded reciprocal weight.

At a shared probe, multiple nearby materials may request different distributions. Building the guide from represented BRDF information is an approximation to their combined demand. Quantization, limited directional bins, support floors, maximum ray weights, and radiance clamps can change the estimator. Do not describe every production probe path as an unbiased ordinary camera-path sample merely because it contains a PDF.

The actual Lumen implementation is a structured refinement scheme. Its normalized incoming-light PDF and BRDF PDF form a sort key. Low-priority ray slots can be reassigned in groups of three to subdivide a higher-priority spherical cell into four children. The default production path uses one refinement level; the serial reference path supports multiple levels. The packed ray information retains that cell and refinement level. The traced results are subsequently reconstructed into the regular directional representation before filtering and integration. The PDF used to rank cells is not a new throughput divisor to apply to that reconstructed radiance. Adding an extra division by it would change the answer. See ray ranking and subdivision and integration of the reconstructed directional field.

Now trace the generated directions through the screen/world hierarchy. An accepted screen hit uses its valid screen-lighting source. A world hit queries the represented surface lighting or selected hit-lighting path. A miss may query the sky. Store the result, hit distance or depth, validity, and any additional flags needed by later filtering. Record whether the stored value is raw radiance, weighted radiance, or a packed trace result. The integration formula must match that storage contract.

Cache distant incoming light in world space

A world-space radiance probe stores a directional incoming field at a point in space. It answers a different question from a card texel: the card stores a surface's approximate outgoing radiance, while the world probe describes what arrives from each direction at a spatial location. Screen probes sample the visible receivers. World probes can share far-field information between those receivers and across camera movement.

Allocate where queries actually need the field

A dense fine grid over the entire world is too expensive. Clipmaps provide a fine region near the view and progressively coarser coverage farther away. Demand marks identify cells needed by current gathers. An indirection texture or buffer maps those cells to physical probe indices. Allocation tracks free entries, last use, update priority, and validity. Scrolling a clipmap changes the relationship between logical cells and world positions, so stale entries cannot simply remain valid under their old coordinates.

Screen-probe placement and cache demand therefore precede the relevant cache update, even though we introduce the cache after explaining a screen probe's query. The implementation schedule is a dependency graph: place receivers, mark demanded world cells, allocate/update selected world probes, then consume the available cache in the remaining traces. Other consumers and retained data can have their own update paths.

For each selected world probe, trace a directional distribution and store radiance plus geometric information needed for parallax and visibility handling. Construct the configured filtered representation and borders so directional lookups remain coherent across seams. The inspected default radiance-cache mip count is one; additional mips are a configurable extension, not an assumed default. An atlas slot with radiance but no valid depth or position record is insufficient for a reliable spatial reconstruction.

Now move the camera a short distance. A world probe can remain at the same world location even though its projected position changes. For a larger move, a clipmap scroll brings new cells into range; a physical atlas slot may eventually be reassigned to one of them. Follow the pair world cell and allocation identity, not just the physical index. For a fixed-camera light change, the opposite experiment is useful: the spatial grid can stay fixed while stored directional radiance changes. Placement, allocation, selection for update, and stored illumination are four distinct observations. A placement overlay alone measures only the first of them.

Implement a small world-probe allocator before adding clipmaps

Start with one bounded 3D grid and a physical pool of P probe slots. Store an indirection index per grid cell, initialized to an invalid sentinel. Store world position, allocation generation, last-used update, last-lit update, and validity per physical slot. The directional radiance and depth atlases use that physical index. The generation prevents a delayed request from mistaking a recycled slot for its previous owner.

A demand pass marks cells touched by queries. A compacted demand list allocates missing slots from a free list. A separate update list selects at most B probes according to a deterministic priority. Clear or initialize every newly assigned slot before any interpolation can consume it. After tracing and filtering, publish its valid state. Retire unused slots only after their current readers have finished; temporal GPU resources cannot be recycled just because CPU code moved to the next line.

For cell size h and grid origin o, a position x has grid coordinate q = (x−o)/h. The integer part identifies neighboring cells; the fractional part supplies interpolation coordinates. A corner with bits (bₓ,bᵧ,b_z) has spatial weight equal to the product of fᵢ for bit 1 and (1−fᵢ) for bit 0. All eight weights sum to one. Missing corners and geometric rejection change that sum, so track the accepted weight explicitly. This elementary implementation is useful for validating addresses and constants; it is not yet sufficient near Sponza's walls.

Add camera-centred clipmaps only after the single grid works. When a grid scrolls, distinguish cells that retain the same world location from new entering cells. Wrapped storage indices alone cannot establish that identity. Allocate, invalidate, and update against world cell coordinates or an equivalent tagged mapping. The engine's concrete indirection layout and budgeting policy refine this same ownership problem.

Why ordinary trilinear interpolation leaks through walls

Take two probes on opposite sides of an arcade wall. Their positions are close, but their incoming fields are different. A distance-only interpolation gives the dark side some of the bright side's field. The weights can sum to one and still be wrong: normalization preserves constants, not discontinuities.

A teaching reconstruction starts with \(\widetilde L_i(x,\omega)=\sum_m w_m(x,\omega)\widehat L_i(x_m,\omega_m)\), with normalized valid weights. The direction \(\omega_m\) may be corrected for the difference between the query point and the probe's observed hit. A depth estimate helps decide whether that correction is plausible and whether the query lies in front of or behind a represented occluder. The actual implementation has specific clipmap selection, coverage tests, fade distances, interpolation weights, and directional/depth sampling rules; substituting a generic eight-probe average loses those conditions.

Local geometry must still be resolved before relying on a distant cache answer. A near wall should occlude far radiance. The trace/cache transition distance and cone footprint determine when a cache approximation is useful. Querying the cache from the origin without local visibility would illuminate the arcade through its own wall.

coverage = choose_cache_clipmap_and_coverage(query_position, ray_cone)
if not coverage.valid: continue_world_trace_or_return_explicit_failure
neighbors = read_probe_indirection(coverage.cell_corners)
for probe in valid(neighbors):
    geometry = read_probe_position_and_directional_depth(probe)
    direction = parallax_correct(query_position, ray_direction, geometry)
    weight = spatial_weight * validity_and_visibility_weight
    value += weight * sample_probe_radiance(probe, direction, mip)
    total_weight += weight
if total_weight == 0: use_documented_fallback
else: value /= total_weight

This pseudocode exposes the required decisions without claiming that every weight is literally multiplied in this order in Unreal. A failed coverage lookup, an unallocated indirection entry, a valid zero-radiance probe, and a rejected geometric contribution are four distinct states. Log them separately. Otherwise a black output cannot tell you which part of the cache failed.
